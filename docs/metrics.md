# Метрики

Что считаем и как. Аналитика сквозная с первой недели разработки: каждое
событие пишется на бэкенде, а не только на клиенте, чтобы цифры не зависели от
блокировщиков и платформы (Telegram / веб).

## Базовые определения

| Термин | Определение |
| --- | --- |
| **Пользователь** | внутренний `user_id`; Telegram-аккаунт и веб-вход одного человека склеиваются в один `user_id` после привязки |
| **Активный пользователь** | совершил хотя бы одно обращение за календарные сутки (МСК) |
| **Обращение** | действие пользователя, на которое система отвечает содержательным шагом: отправка вопроса, раскрытие карты, ответ на уточняющий вопрос, вытягивание карты дня, вечерняя сверка. Открытие приложения и навигация обращениями не считаются |
| **Сессия** | последовательность событий пользователя без перерыва дольше 30 минут |
| **Слой** | `spread` (большой расклад) или `daily` (карта дня); у каждого обращения есть слой |

## Метрики

### DAU

Число уникальных активных пользователей за сутки. Норматив этапа 1 —
ориентир в 1000 DAU; на закрытом запуске важна динамика и структура, а не
абсолют.

### Обращения на 1 DAU

`обращения за сутки / DAU за те же сутки`. Считается в целом и отдельно по
слоям. Ожидание по механике: 8–12 на большой расклад, 1–3 на карту дня.

### Сессии

- Число сессий на активного пользователя в сутки.
- Длина сессии — медиана и p75 по времени (от первого до последнего события)
  и по числу обращений.

Медиана, а не среднее: несколько очень длинных сессий не должны маскировать
типичное поведение.

### Воронка первого расклада

По новым пользователям, шаги в порядке:

1. Открыл продукт (первое событие `app_open`).
2. Отправил вопрос.
3. Раскрыл первую карту.
4. Ответил на первый уточняющий вопрос.
5. Раскрыл все карты расклада.
6. Дошёл до итога.
7. Вернулся в течение 7 дней (любое обращение).

Для каждого шага — конверсия от предыдущего и от первого, плюс медианное
время между шагами. Главные точки потерь, которые ищем: шаг 2 (не понял, что
делать) и шаг 4 (диалог воспринимается как лишний).

### Retention D1 / D7 / D30

Когорта — пользователи по дню первого обращения. D*N* — доля когорты, у
которой было хотя бы одно обращение ровно на *N*-й день после первого.
Дополнительно считаем rolling-вариант («хотя бы раз в дни 1…*N*»), но решения
принимаем по классическому.

D30 на этапе 1 полностью не наблюдается (запуск 13–15.10) — фиксируем
методику, данные появятся после этапа.

### Разделение по слоям

Все метрики выше считаются в трёх срезах: только `spread`, только `daily`, оба
слоя. Ключевые вопросы этапа 1:

- Какая доля DAU приходит только ради карты дня.
- Повышает ли наличие незакрытого расклада возврат к карте дня
  (retention пользователей с открытой ситуацией против без неё).
- Какая доля вечерних сверок совершается после утренней карты.

## Антифрод-разметка источников

Цель — чтобы метрики этапа отражали реальных людей, а не накрутку, и чтобы
каждый канал можно было оценить отдельно.

- **Метка источника.** Каждый вход несёт параметр источника (`start_param` в
  Telegram, `utm_source` в вебе). Первая метка закрепляется за пользователем
  навсегда (first touch), последующие пишутся как события.
- **Реферальная атрибуция.** Шеринг результата содержит идентификатор
  отправителя — видно, какие приглашения конвертируются.
- **Флаги подозрительной активности** (пользователь не удаляется, а
  помечается и исключается из отчётных срезов):
  - всплеск регистраций из одного источника за короткое окно;
  - аккаунты без единого содержательного обращения после входа;
  - обращения с нечеловеческой скоростью (интервалы короче времени чтения
    ответа);
  - повторяющиеся идентичные тексты вопросов от разных пользователей.
- **Отчёты** строятся в двух вариантах: все пользователи и очищенные от
  флагов. Расхождение между ними само по себе — сигнал по каналу.

## Стоимость

Отдельная метрика с первой недели: стоимость LLM-вызовов на активного
пользователя в сутки и на один большой расклад, с разбивкой по шагам
(классификация, интерпретация, проверка). Нужна для оценки масштабирования до
1000 DAU.

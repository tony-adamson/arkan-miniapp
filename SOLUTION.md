# Блок 1. Для человека

## 1. Что нужно сделать

К 13–15.10.2026 собрать MVP «Аркан» — ИИ-таролога в формате диалога (Telegram
Mini App + веб, один фронтенд) — и запустить его закрыто на 50–100 человеках,
чтобы ответить на главный вопрос этапа 1: существует ли рядом с редкой глубокой
потребностью ежедневная. Всё, что до этого момента было в репозитории
документами (продукт, метрики, дизайн-система, лендинг), становится работающим
продуктом. Выигрыш — проверенная гипотеза и цифры для акселератора; проигрыш —
дедлайн 15.10.

## 2. Короткое решение

Один backend-процесс на FastAPI: HTTP API, поллинг Telegram-бота и вечерние
напоминания живут в нём же, без отдельных воркеров. Вокруг него — Postgres
(пользователи, расклады, события, стоимость LLM), Redis (лимиты и антифрод),
Qdrant (экспертная база) и статический фронтенд из готовой дизайн-системы.
Карты выбирает детерминированный движок с сохраняемым сидом до любого обращения
к модели. Толкование собирается через RAG по экспертной базе Анастасии
(формулировка — DeepSeek-V4.1-Flash за конфигом с адаптером на GigaChat/Qwen)
и перед показом проверяется на соответствие базе; непроверенное не показывается
никогда — вместо него эталонный текст из базы. Аналитика серверная с первого
дня: обращения, сессии, воронка, retention, антифрод и стоимость токена
считаются из таблиц, дашборды в Grafana.

## 3. Что мы НЕ делаем

- NG-1. Монетизация и платежи.
- NG-2. Перевёрнутые карты, LLM-генерация уточняющих вопросов, кэш и предгенерация
  толкований.
- NG-3. i18n, часовые пояса кроме МСК, наследование темы Telegram.
- NG-4. Веб-пуши, публичные страницы шеринга, настраиваемое время напоминаний.
- NG-5. Админ-панель (Grafana + SQL), автоматический деплой, Alertmanager.
- NG-6. «Спросить через месяц, что изменилось» — D30 на этапе 1 всё равно не наблюдается.
- NG-7. Локализация ПДн в РФ и отказ от зарубежного провайдера модели —
  юридический риск принят пользователем для MVP (17.09.2026, R9); этап 2 —
  RU VPS и собственные мощности под DeepSeek/Qwen (neuraldeep) через тот же адаптер.

## 4. Почему это не overengineering

- Минимальный вариант: один backend-процесс, шесть сервисов Docker Compose
  (api, postgres, redis, qdrant, prometheus, grafana) за системным nginx, ноль
  очередей и воркеров; бот на голом Bot API через httpx без
  бот-фреймворка.
- Переиспользуемое: дизайн-система (токены + 12 компонентов + экраны UI-кита)
  переносится как есть, UX и тексты — из GUIDE.md, лендинг и nginx-инфраструктура
  уже живут на целевом сервере.
- Новые подсистемы: только продиктованные требованиями — векторный поиск (суть
  продукта), редис-лимиты (антифрод из metrics.md), cron-напоминания (решение Q8).
- В future work: связки карт, перевёрнутые, GigaChat-адаптер, расширение
  категорий, RU VPS и self-hosted модели (этап 2).

## 5. Риски и проверки

- Главный риск реализовался: fornex-de (17.09) — 3.8 ГБ RAM, свободного
  запаса нет, а стек с BGE-M3 и реранкером требует ~6 ГБ. Где разворачивать
  MVP отложено (DEC-1): разработка идёт локально в Docker Compose, хост —
  параметр деплоя; решение нужно до первого деплоя.
- DeepSeek-платёжка из РФ проверяется первым пополнением; запасной план — GigaChat
  (рубли) или self-hosted DeepSeek/Qwen на своих мощностях через тот же адаптер.
- Юридический риск (ПДн вне РФ, передача текста вопросов провайдеру в КНР)
  принят для MVP; до запуска приводится в соответствие текст privacy, который
  сейчас обещает хранение в РФ (R9).
- Кризисные сигналы проверяются в каждом тексте пользователя, не только в
  первом вопросе.
- Качество толкований: ревью 50 случаев экспертом на неделе 22–28.09 —
  эталон из docs/expert-brief.md.
- Проверка результата: сквозной e2e-сценарий полного расклада, property-тест
  воспроизводимости сида, воронка и стоимость на Grafana после запуска.

## 4. Релевантный текущий контекст

Greenfield-часть — весь прикладной код. Существующие ограничения:

- **Дизайн-система** (`design-system/`): токены (канон —
  `landing/site/assets/css/tokens/`, зеркало — `design-system/tokens/`, правки
  синхронны в обеих копиях), 12 React-компонентов с `.d.ts`-контрактами, UI-кит
  `ui_kits/arkan-miniapp/` со всеми 7 экранами MVP и живой анимацией раскрытия
  (`Reading.jsx`). Компоненты «переносятся в приложение как есть».
- **Тон и UX**: GUIDE.md — обращение на «вы», точка всегда, без восклицательных
  и эмодзи, 2–4 строки на реплику, кнопки 1–3 слова, чипы до 4 слов.
- **Лендинг**: статический, уже на целевом nginx (`deploy/nginx.conf.example`),
  CTA `/soon/` ждёт ссылку на бота, `add_header` только на уровне `server`,

- **Privacy-черновик** (`landing/site/privacy/`): сайт ничего не собирает;
  приложение собирает — согласие в онбординге закрывает. Раздел 7 сейчас
  утверждает хранение ПДн в РФ (152-ФЗ ч.5 ст.18) — фактической схеме MVP (DE)
  это противоречит; разделы 6 (провайдер модели: DeepSeek, КНР) и 7 привести к
  факту перед запуском (R9).
- **UI-кит-поток**: онбординг (3 шага + согласие) → вопрос → расклад
  (ожидание/рубашка/раскрытие/толкование/уточнение) → итог → история →
  карта дня → профиль (переключение темы, модалка удаления).
- **Существующих контрактов прикладного кода нет** — регрессионной поверхности
  нет; контракт, который нельзя ломать, — лендинг и токены.

## 8. Рассмотренные альтернативы

### Вариант 0: минимальный локальный рост

- **Суть**: всё, что можно, из существующего: фронт = UI-кит + токены; тексты =
  GUIDE; деплой = существующий nginx форнекса; метрики = SQL поверх событий;
  бот/напоминания = задачи в api-процессе; без новых подсистем.
- **Покрывает**: все REQ; риски закрываются fallback-ами.
- **Плюсы**: минимальный diff к дедлайну, один ревьюер справится.
- **Минусы**: нет — минимальный и выбран.
- **Обратимость**: каждый слой удаляем отдельным compose-сервисом.
- **Выбран**.

### Вариант A: «правильная» композиция (api + bot + worker + embedding сервисы)

Отклонён: 3 контейнера и 2 границы RPC без единого требования, кроме них
требующего. NFR-1 покрывается in-process ONNX; напоминания — asyncio-задача.

### Вариант B: толкования без LLM (тексты базы напрямую)

Отклонён: продукт продаёт формулировку под ситуацию и историю пользователя —
конкуренты так и работают, product.md называет это главной слабостью ниши.
LLM оставлена, но зажата проверкой и fallback-ом в базу.

### Вариант C: интерпретации с эмбеддинг-API вместо self-host

Отклонён: CON-1 фиксирует BGE-M3 self-host; факт-чек подтвердил CPU-режим.
Адаптер эмбеддингов не вводится (один провайдер и так local) — сигнал вернуться:
RAM-нехватка ASM-1.

## 9. Рекомендованное решение

### 9.1 Сводка

FastAPI-монолит (API + бот + напоминания), Postgres, Redis, Qdrant, статический
React-фронт из дизайн-системы, LLM = DeepSeek-V4.1-Flash за адаптером,
RAG по экспертной базе с проверкой перед показом, детерминированная колода,
серверная аналитика и антифрод, Grafana. Развёртывание Docker Compose на
fornex-de рядом с лендингом, Mini App на app.arkana.hoapps.dev.

### 9.2 Архитектура и ответственность

```
[Telegram MA | web]
      │ https (nginx, static фронт + reverse-proxy /api)
      ▼
[api: FastAPI]──┬── HTTP: REST, cookie-сессии, initData-валидация
                ├── engine: колода (чистые функции, сид), spread-машина
                ├── pipeline: классификация → RAG → генерация → проверка
                ├── bot: поллинг Bot API (httpx), /start, кнопка MA
                ├── cron: напоминания 19:00 МСК (asyncio, отметка отправки в PG)
                ├── rag: onnxruntime BGE-M3 + bge-reranker (in-process)
                └── events/antifraud: запись событий, Redis-лимиты, флаги
      ▼                ▼                ▼
[Postgres]        [Redis]          [Qdrant]
   ▲                                                     ▲
[api: /metrics] → [Prometheus] → [Grafana]
```

Процесс api запускается строго одним uvicorn-воркером: бот-поллинг и cron живут
в нём же, второй воркер удвоит поллинг и напоминания. Горизонтальное
масштабирование на этапе 1 не требуется (ASM-6).

Ответственности: фронт — только отображение и адаптер платформы; вся логика,
состояние и события — на бэкенде (CON-7); колода — чистая функция от сида
(NFR-3); источником смысла всегда экспертная база (REQ-6).

### 9.3 Сквозной поток (большой расклад)

1. Онбординг: согласие → `POST /auth/…` создаёт user (веб: анонимная cookie-сессия
   выдаётся раньше, на первом обращении, чтобы `app_open` воронки писался до
   согласия; Telegram: валидация initData HMAC-SHA256, auth_date ≤ 24 ч).
2. `app_open` с источником (start_param/utm) → first touch фиксируется навсегда.
3. Вопрос → `POST /spreads` → шаг классификации (LLM, JSON; в контексте —
   профиль, см. ниже): тема → структура, вопрос вне трёх тем → `choice`;
   `medical|psychotherapy|legal|financial` → отказ; `crisis` → кризисный экран
   (REQ-2/3/4).
4. При создании расклада движок сразу тянет все карты: seed = 32 байта OS CSPRNG,
   сохраняется; порядок карт = чистая функция Fisher–Yates поверх HMAC-потока
   сида (NFR-3). Модель ещё не вызвана ни разу (REQ-5).
5. `POST /spreads/{id}/reveal` для позиции N: смысл карты берётся точно, без
   семантики — поля `card_id` (общее значение + значение по теме расклада +
   `not_to_say`) фильтром payload в Qdrant; семантический поиск (запрос = вопрос +
   позиция + ответы 1..N-1 → BGE-M3 → top-10 → реранкер → top-4) идёт только
   внутри этой карты и по правилам/примерам эксперта → генерация DeepSeek (правила тона + чанки → 2–4
   предложения; thinking по умолчанию отключён ради NFR-1 — конфиг
   `LLM_THINKING`, решение о включении принимается по итогам ревью 50 случаев)
   → проверка → показ или fallback в базу. Идемпотентно: одна позиция — одна
   интерпретация, повторный вызов возвращает сохранённую.
6. Уточняющий вопрос позиции из expert-brief (`ask_1|ask_2` детерминированно
   по сиду; пустой `ask_2` → всегда `ask_1`) + чипы; свободный ответ принимается
   наравне (REQ-7). Свободный текст проходит кризис-проверку (стоп-паттерны +
   шаг `classification`); при `crisis` расклад закрывается и показывается
   кризисный экран (REQ-4). Ответ чипом проверку не проходит.
7. Следующая позиция: ответы входят в контекст (REQ-8). Повтор 5–6.
8. Итог: сводка всех позиций с учётом ответов → сохранение → «вернуться».
9. Сбой LLM на любом шаге: позиция остаётся нераскрытой, расклад не теряется,
   повтор retries генерацию (NFR-5, тексты ошибок из GUIDE).

Карта дня: seed = HMAC(server_secret, `user_id:date_МСК`) — одна карта на сутки,
повторное открытие возвращает её же; утренний текст — LLM по `meaning_daily` в
контексте последнего незакрытого расклада; вечерняя сверка — текст из
`checkin_texts` (детерминированно по дате) + чипы/свободный ответ; свободный
ответ проходит кризис-проверку; затем шаг `checkin` — модель пишет отклик в 1–2
предложения по `meaning_daily`, утреннему тексту и ответу, отклик проходит ту же
проверку, что толкование (D7); провал проверки → нейтральная фраза `closing` из
`checkin_texts` (REQ-11). Бот в 19:00 МСК шлёт
напоминание включившим (REQ-20).

Профиль (product.md «Память») — не отдельная таблица, а выборка: итоги и
ответы последних 3 раскладов пользователя; входит в контекст классификации,
толкования и утренней карты дня (REQ-10).

### 9.4 Данные и состояние

Postgres (SQLAlchemy 2 + Alembic; сутки везде МСК):

- `users`: id, public_ref (короткий, для шеринга), created_at, consent_at,
  first_source, push_enabled, last_reminder_date (сутки МСК последнего
  напоминания), telegram_id (nullable, unique)
- `sessions`: id (cookie), user_id (nullable до согласия), created_at, last_seen
- `spreads`: id, user_id, structure_type, question, category, status
  (`active|completed|abandoned`), seed, created_at, completed_at, summary
- `spread_positions`: spread_id, position_number, card_id, revealed_at,
  interpretation, verify_status (`passed|fallback`), ask_variant, ask_answer
- `daily_cards`: user_id, date, card_id, morning_text, drawn_at, checkin_variant,
  checkin_answer, checkin_reply, checked_at (PK user_id+date)
- `events` (append-only): id, user_id (nullable), session_id, type
  (`app_open|question_sent|card_revealed|clarifying_answer|summary_viewed|
  daily_drawn|daily_checkin|shared|push_opened|refusal_shown|crisis_shown`), layer
  (`spread|daily|null`), payload JSONB, created_at
- `llm_calls` (append-only): id, user_id, spread_id, step
  (`classification|interpretation|verification|summary|daily|checkin`), model,
  tokens_in/out, cost_usd, status, created_at
- `fraud_flags`: user_id, flag, reason, created_at

Redis (эфемерное): rate-лимиты обращений, счётчики антифрода (регистраций по
источнику/день, скорость обращений, hash-нормализованных вопросов). Qdrant:
коллекция `expert_base` (~700 чанков: карта×тема, позиции, правила, примеры;
payload `card_id`, `topic`, `kind`), предвычисляется скриптом ingest из YAML
экспертной базы.

Незакрытых раскладов может быть несколько (UI-кит, история со статусом
`unfinished`): новый вопрос не закрывает прежний, любой продолжается из истории с
первой нераскрытой позиции (REQ-10). Статус `abandoned` ставится только при
кризисе. Карта дня привязывается к последнему незакрытому раскладу.

### 9.5 Контракты

REST API (19 эндпоинтов): `POST /auth/anonymous`, `POST /auth/telegram`,
`POST /auth/consent`, `POST /auth/link/code` + `GET /auth/link/status`;
`POST /spreads`; `POST /spreads/{id}/reveal`; `POST /spreads/{id}/answer`;
`POST /spreads/{id}/summary`; `POST /spreads/{id}/share`; `GET /spreads`;
`GET /spreads/{id}`; `GET /daily`; `POST /daily/draw`; `POST /daily/checkin`;
`POST /events` (только `app_open|push_opened`); `GET/DELETE /profile`;
`PATCH /profile/settings`. Плюс внутренний `/metrics`, наружу не публикуется.
Идемпотентность `POST /spreads` — заголовок `Idempotency-Key`, ключ хранится в
Redis с TTL 10 мин.
Все мутации пишут события; ошибки в тонах GUIDE («Связь прервалась. Расклад
сохранён — можно продолжить с той же карты.»). Контракты наружу: формат
экспертной базы — docs/expert-brief.md (CSV→YAML, валидатор), совместимость
лендинга и nginx, тёмная тема по умолчанию.

### 9.6 Поведение при отказах

- LLM таймаут/5xx: retry ×1 → позиция нераскрыта, фронт показывает «дыхание»
  (RitualLoader) и кнопку повторить; расклад цел (NFR-5).
- Проверка провалилась: одна перегенерация; провалилась повторно —
  fallback-толкование = эталонное значение карты по теме из базы;
  `verify_status=fallback`; событие фиксирует замену (REQ-6). Максимум на позицию —
  2 генерации + 2 проверки (учтено в NFR-2).
- Qdrant/ONNX недоступны: толкование сразу из базы без генерации (деградация
  качества без деградации сервиса).
- Redis недоступен: лимиты пропускаются (fail-open), события пишутся в PG —
  антифрод считается по факту за ретроспективный период.
- Postgres недоступен: 5xx, фронт — ErrorState из дизайн-системы.
- Бот-напоминание неуспешно: пометка в лог, повтор на следующем цикле того же
  дня. Отправка и `users.last_reminder_date` пишутся вместе; цикл берёт только
  пользователей с `last_reminder_date < сегодня МСК`, поэтому рестарт процесса
  не дублирует и не теряет напоминание (догоняет до 23:00 МСК).

### 9.7 Платформенные аспекты

- **Mini App**: официальный `telegram-web-app.js`, адаптер фронта
  (`TelegramAdapter | WebAdapter`): initData, haptic, share; тема не наследуется
  (своя палитра самодостаточна, NG).
- **Веб**: тот же бандл, `WebAdapter`, cookie HttpOnly+Secure+SameSite=Lax.
- **Шрифты/иконки**: самохост woff2 (уже в репо), иконки Lucide — статическая
  копия в бандл (лендинг живёт без CDN, приложение тоже).
- **nginx**: отдельный `server` под app.arkana.hoapps.dev, `add_header` только
  на уровне `server`, CSP как у лендинга; деплой статички симлинк-схемой лендинга.

### 9.8 Совместимость, миграция, развёртывание

Greenfield — миграций существующих данных нет. Alembic с первого коммита.
Развёртывание: GH Actions (lint/typecheck/tests/build) → ручной деплой
(`git pull && docker compose up -d --build` на форнексе), скрипт с бэкапом
`pg_dump` перед подъёмом. Откат = `alembic downgrade` до ревизии предыдущего
тега (или restore дампа, если миграция необратима) + предыдущий тег +
`compose up -d`. Nightly и предрелизный дамп копируются за пределы коробки.

### 9.9 Безопасность, приватность

Согласие до создания аккаунта (REQ-18); initData проверяется HMAC-SHA256 с
ключом `HMAC_SHA256("WebAppData", bot_token)`, токен бота в .env;
секреты только в .env/.github secrets; rate-лимиты (Redis: LLM-обращения
на пользователя, анти-«нечеловеческая скорость» из metrics.md); удаление
аккаунта — каскад + анонимизация `events.user_id` (метрики сохраняются, ПДн
удаляются); доступ к сервисам изнутри compose-сети, наружу — только nginx.
ПДн в DE и текст вопросов у провайдера в КНР — принятый юридический риск MVP
(ASM-5, R9). До запуска privacy приводится к факту: раздел 6 — DeepSeek, КНР;
раздел 7 — сейчас обещает хранение в РФ, это нужно переписать. Этап 2 — RU VPS
для PG и self-hosted DeepSeek/Qwen на своих мощностях через тот же адаптер.

### 9.10 Наблюдаемость и эксплуатация

`/metrics` (prometheus-client: HTTP-гистограммы, LLM-шаги, токены, fallback-рейт,
5xx). Grafana: DAU, обращения/1 DAU по слоям, воронка 7 шагов, retention
D1/D7, стоимость на DAU, p95 reveal. SQL-вьюхи метрик = единственный источник
цифр этапа 1 (CON-7). Нагрузка недели 4: k6-скрипт пик-модели 1000 DAU.

## 16. Результаты челленджеров

### Design Challenger

- **Находки**:
  1. BLOCKING: `app_open` до согласия не имел user_id — воронка шага 1 терялась.
     Исправлено: сессия-куки выдаётся до согласия, события пишутся на сессию.
  2. BLOCKING: reveal без идемпотентности — двойной тап = двойная генерация
     и двойная стоимость. Исправлено: интерпретация создаётся один раз на позицию.
  3. BLOCKING: конфликт привязки Telegram (два user_id претендуют на один
     telegram_id) не был определён. Исправлено: отказ привязки, код перевыдаётся.
  4. NON_BLOCKING: тайминг напоминаний не привязан к МСК-суткам карты дня —
     уточнено (слот 19:00 МСК, событие push_opened отдельно от organic app_open).
  5. NON_BLOCKING: напоминания бот шлёт и не открывавшим приложение давно —
     уточнено: opt-out в профиле + only users с включённым пушем.
  6. BLOCKING: в списке API отсутствовал эндпоинт вытягивания карты дня
     (`GET /daily` не покрывал draw-семантику §10). Добавлен `POST /daily/draw`
     (идемпотентный на сутки МСК).
- **Принятые правки**: внесены в §9.3, §9.4, §10, §11.
- **Отклонённые находки**: «нужен rate limit по IP для анонимов» — оставлен
  per-session лимит: для 50–100 закрытых пользователей достаточно, по IP в РФ
  адреса общие, и флаги ложились бы на непричастных.

### Lean Challenger

- **Находки overengineering**:
  1. aiogram → голый Bot API (принято, D9).
  2. APScheduler → asyncio-cron (принято, §9.2).
  3. Кэш интерпретаций — отклонён заранее (§5.3).
